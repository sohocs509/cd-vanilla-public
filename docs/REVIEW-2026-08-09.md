## 1. Blocking — must fix before publication

### F1. The spec says `base64url`; the implementation is standard `base64`. They are incompatible.

`SPEC.md` specifies `base64url` in **23 places** — `iv`, `ciphertext`, `eph_spki`, `hkdf_salt`,
`ct`, `salt`, `credential_id`, `prf_salt`, `prev_hash`, `payload_hash`, `spki`, `pkcs8`.
The reference implementation uses `btoa`/`atob` (`cell-crypto.js:12-21`), which is **standard
base64** with `+`, `/`, and `=` padding.

This is not cosmetic. `atob()` **throws** on a `-` or `_`:

```
toB64 output    : +/++PtA=      ← real output, contains + / =
base64url form  : -_--PtA
atob(base64url) : InvalidCharacterError: Invalid character
```

An implementer who follows the specification literally — exactly the reader the defensive
disclosure is written for — produces cells the reference implementation **cannot open**, and
cannot open cells the reference implementation produces. Confirmed present in the real
artifacts: `fig-quorum.cell`'s ciphertext contains `+` and `/`.

Propagated to `DEFENSIVE-DISCLOSURE.md` (23) and to the companion book (42 occurrences across three
chapters). Disclosure §7.10 compounds it by reciting
"Base64url encoding may be substituted…" as though base64url were what is used.

**Fix:** replace `base64url` with `base64` throughout, or change `toB64`/`fromB64` and re-stamp.
Given cells already exist in the wild, correcting the *documents* is the safe direction.

### F2. `header_hash`, `payload_hash` and signature verification are all skippable.

`cell-crypto.js:791` guards the entire integrity block on `if (cell.header && cell.header_hash)`.
Delete the `header_hash` field and every check inside — including `payload_hash` and the ECDSA
signature — is silently skipped. Demonstrated:

```
1) corrupt payload_hash                   -> refused: "Integrity check failed"
2) header_hash DELETED + bad payload_hash -> OPENED: secret.txt | "TOP SECRET CONTENTS"
3) signature STRIPPED from signed cell    -> OPENED, sigVerified = null, no warning
```

Scope this honestly: it is **not** a plaintext-recovery break. AES-GCM still authenticates the
ciphertext and the AAD-bound metadata, so an attacker cannot alter content, `lifetime`, `policy`,
`threshold`, or `prev_hash`. What it does defeat is everything the AAD deliberately does *not*
cover — `access_map` and `payload_hash` (§4.4 says so explicitly, and points at
`header_hash`/`header_sig` as their protection) — plus sender attribution, since a signed cell
downgrades to an unsigned one indistinguishable from a never-signed one.

This makes SPEC §10's summary overstated as written: *"Together they detect any tampering with
the header, the metadata, or the ciphertext."*

**Fix:** make `header_hash` mandatory for v1.1+ (reject its absence), and give callers a way to
require a signature. Then state in §10 that an absent `header_hash` is a rejection, not a skip.

### F3. The OTS priority claim is true but **not verifiable from the repository as committed**.

Both the companion book and `DEFENSIVE-DISCLOSURE.md:783-790` state all
three artifacts are "Bitcoin-confirmed 2026-07-19" in blocks **958650** and **958690**.

The digests are all correct — verified against `git show cell-format-v1.2-defensive-pub`:

The tag `cell-format-v1.2-defensive-pub` and commit `62a8143` both exist and match.

**But the committed proofs do not show the anchors.** At that tag, all three `.ots` files are

## 2. False or contradicted statements

### F4. "N-1 shares reveal nothing" — wrong, should be M-1.

`SPEC.md:667`, `DEFENSIVE-DISCLOSURE.md:637`, `90-appendix-a-spec.md:595`:

> Threshold access | Shamir SSS — M shares required, **N-1 shares reveal nothing**

For a 2-of-3 cell, N-1 = 2 shares, which is exactly the reconstruction threshold. The security
table states that a quorum's worth of shares reveals nothing. It should read **"fewer than M"**.
The same documents get this right elsewhere (SPEC §7 "fewer than M shares reveal nothing";
disclosure §6.2 "any fewer than M shares"), so this is an isolated slip in the one table a
skimming evaluator is most likely to read.

### F5. `SPEC.md` is v1.3 but is labelled v1.2 in ten places.

Title line 1 still reads *"Cell Format Specification v1.2"*. Also: `§4.1` example shows
`"version": "1.2"` (§15's full example correctly shows `1.3`); `§4.1.1` is headed "Canonical
serialization (v1.2)"; `§4.1`, `§4.4`, `§10`, `§14`, `§16` all say "for v1.2" where the code uses
the sets `CANONICAL_VERSIONS = {1.2, 1.3}` and `AAD_VERSIONS = {1.1, 1.2, 1.3}`; `§15`'s heading
says "A minimal v1.2 cell" above a `1.3` document.

This is the exact failure mode §12 warns about in prose — an inline `1.2` left behind after a
version was added to the set — reproduced in the specification's own text.

### F6. The defensive disclosure is stale against the spec it claims to reproduce.

`DEFENSIVE-DISCLOSURE.md:43` states the reproduced text is *"the `.cell` v1.2 format
specification, reproduced in full from `docs/SPEC.md`"*. As of commit `29f4ef3` (today, 19:10)
`docs/SPEC.md` is **v1.3**; the disclosure was last built at 18:19 and still carries the v1.2
text — flat `lifetime`, `expires_at`/`on_expiry`, changelog ending at "1.2 (editorial)".

The document is dated **2026-08-09**, so a reader gets a same-day document that describes a
superseded revision while asserting it reproduces the current file. §5's careful paragraph about
exactly-what-is-anchored is excellent and should be extended to cover this: either re-anchor on
v1.3, or state plainly that the disclosure pins v1.2 deliberately and that v1.3 exists.

Same issue in the companion book: its normative spec appendix is titled "The .cell v1.2
Specification (Normative)" and three chapters still use the v1.2 flat lifetime shape.

### F7. The versioning chapter uses `1.3` as its example of an *unrecognized* version.

In the companion book:

> An opener that meets a `version` string it does not recognize — **a `1.3`**, a `2.5`, some
> future revision — does not guess.

`1.3` is now `CELL_FORMAT_VERSION`, the version every new cell is written as. The illustration
now says the current format is unopenable. Change to `1.4`/`2.5`.

### F8. `cell-crypto.js` declares itself proprietary; everything else says AGPL.

`cell-crypto.js:2`:

```
// SPDX-License-Identifier: LicenseRef-Enthropic-Proprietary
```

`LICENSE` is AGPL-3.0, `LICENSING.md` §2 names `cell-crypto.js` explicitly as AGPL, the book's
copyright page says AGPL, and disclosure §11 says AGPL. The SPDX tag is machine-readable and
authoritative to tooling — a license scanner will report this file as proprietary. It was missed
in `b37879a`. `package.json` also has no `license` field.

## 3. Omissions and smaller inaccuracies

### F10. The ECDSA signature encoding is never specified — and it blocked independent verification.

This is the one place the enablement claim actually failed in practice. My spec-only verifier
reproduced `header_hash`, `payload_hash` and the fingerprint on the first attempt, but
`header_sig` **failed** until I guessed the encoding.

WebCrypto emits **raw r‖s (IEEE P1363), 64 bytes**. Most general-purpose libraries — OpenSSL,
Python `cryptography`, Go, Java — expect **DER**. The spec says only "base64 ECDSA-SHA256
signature" (§4.1) and "ECDSA P-256 + SHA-256" (§14). Once converted, both cells verify:

```
fig-quorum.cell -> sig len 64, raw r||s (P1363), NOT DER; verifies: PASS
fig-child.cell  -> sig len 64, raw r||s (P1363), NOT DER; verifies: PASS
```

Add to §4.1/§14: *"`header_sig` is the raw 64-byte r‖s concatenation (IEEE P1363), not DER."*
Worth noting this is evidence *against* disclosure §9's claim that the figures were reproduced
"using a general-purpose cryptographic library" — such a library would have hit exactly this.

### F11. `share_index` is omitted, not `null`, for non-quorum cells.

Spec §6.1/§6.4 say `"share_index": <integer> | null` and "For non-quorum cells … `share_index`
is `null`". `_wrapEntry` (`cell-crypto.js:630`) only sets the key when a share index exists, so
the field is **absent**. Since `access_map` feeds `header_hash` via canonicalization, an
implementer who writes an explicit `null` gets a different (self-consistent, still valid) hash.
Harmless but the spec should describe what the code does.

### F12. Verification order in §10 does not match `cellOpen`.

SPEC §10 lists integrity checks 1–3 and says *"Steps 1–3 run before decryption"*; §4.1 says
`header_hash` is *"verified on open before any decryption"*. Ch 17 goes further: three refusals
*"before doing anything at all"*, praising the discipline of cheap checks first.

`cellOpen` actually runs **key unwrapping and quorum reconstruction first** (lines 761-787), then
integrity (789-812), then body decrypt (817). For a passphrase cell that means a full
**PBKDF2 600,000-iteration derivation** runs before `header_hash` is ever checked — and AES-KW
unwrap is itself a decryption. Only the *advisory lifetime* checks genuinely run first.

Either move the integrity block above the unwrap loop (preferable, and it would make Ch 17 true),
or correct §10, §4.1 and Ch 17 to say integrity is verified before *body* decryption.

## 5. What holds up

Worth recording, because most of it does:

- **The cryptographic construction is sound and correctly described.** ECDH→HKDF→AES-KW, the AAD
  binding, canonicalization, GF(256) Shamir, version-gating — all match the code.
- **The digests and the tag are genuine.** All three SHA-256 values verify; the anchors exist.
- **The honesty discipline is real, not decorative.** The advisory/enforced split (§8), the
  unkeyed-`header_hash` caveat (§4.1), the `header_sig_by` trust note, disclosure §8's four scope
  limitations, and §10's own admission that provable existence ≠ public accessibility are all
  accurate and unusually candid. F2 and F12 are places where the *code* falls short of that
  standard, not the prose.
- **The §3 historical anchors are accurate.** Lavabit (2013, TLS key surrender), MOVEit (2023,
  SQL injection), Hushmail (2007, server-side passphrase capture) are all correctly characterized.
- **`lifetime` is genuinely checked before any crypto**, as Ch 15 claims — that one is true.
- **49/49 tests pass.**
